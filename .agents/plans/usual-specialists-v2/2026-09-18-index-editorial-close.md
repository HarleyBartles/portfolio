## Responsive Composition Contract

Start from the existing `indexResponsive.ts` vocabulary, but do **not** treat every
existing query threshold as an independently justified design band. This milestone
must audit the responsive vocabulary while recomposing Index.

The design-level composition families are mobile-first:

- default / `320–389`: narrow survival;
- `min-width: 390px`: compact composition through 767px;
- `min-width: 768px`: one medium composition family through 1399px;
- `min-width: 1400px`: one wide composition family through 1919px; and
- `min-width: 1920px`: ultrawide one-screen composition, with geometry frozen above
  2560px.

Use `min-width` consistently for authored transitions. Do not mix equivalent
`max-width: 767px` / `min-width: 768px` boundary definitions across components unless
an isolated browser workaround genuinely requires it. Narrow is the default state;
larger authored states layer on progressively.

The existing `900` and `1600` thresholds are **not** automatically design bands.
They are provisional implementation thresholds. Keep either only when it has a
self-contained reason that can be stated in terms of story, hierarchy, available
content or a deliberate composition mode. "Things overlap here, so move them" is
not sufficient justification.

An adjustment threshold is legitimate when, for example:

- a previously hidden narrative figure/beat becomes intentionally available at that
  width and changes the composition hierarchy;
- a panel changes role from stacked to overlapping, or from supporting insert to
  lateral sequence, because there is enough field to support that mode;
- a legibility requirement permits/restores a meaningful asset at a minimum useful
  size; or
- the threshold is required to satisfy the explicit `1920+` one-screen cadence
  without disturbing the composition family below it.

An adjustment threshold is **not** legitimate when its only rationale is a set of
unrelated pixel nudges accumulated to repair local collisions. In that case, prefer
fluid sizing/positioning with `clamp()`, percentages, Grid/Flex relationships, or
container-relative geometry inside the containing composition family. If the live
wireframe cannot produce a stronger reason for an existing threshold, remove or
collapse it rather than preserving historical CSS by inertia.

| Band | Intended Index composition |
| --- | --- |
| `320–389` (`narrow`) | Preserve the document field as a dense vertical terrain, with the passive Silk rope still behind it. Keep the story card before the closing sequence in source order and let it read as an early editorial orientation rather than the last item. The closing sequence becomes predominantly vertical: observation first; the `“Ah. This one.”` rectangle touches/bridges the transition into the source-retrieval panel; retrieval follows with only modest overlap; the outcome panel lands last with the yellow note fully readable and the blue fold visible. Do not force a three-panel desktop collage into this width. No horizontal overflow. |

The observation and retrieval panels may overlap diagonally more than at 320, with the recognition rectangle literally occupying their seam. The outcome panel follows as the terminal beat, offset enough to keep the composition messy but not buried under retrieval. The note remains the strongest read in that final panel. |

### Breakpoint justification record

Before finalising responsive CSS, the implementer must leave a short justification
comment beside every retained named threshold in `indexResponsive.ts` (or in the
closest owning styles file if the query vocabulary remains centralised). The comment
must answer **what changes in the composition at this threshold and why that change is
valuable to the story/read**, not merely name the elements that were colliding.

The expected starting disposition is:

| Threshold | Starting judgement | Required justification to retain |
| --- | --- | --- |
| `390` | justified design boundary | Narrow survival gives way to a materially roomier compact composition with different overlap capacity. |
| `768` | justified design boundary | Compact/portrait stacking gives way to a genuine two-dimensional medium field where observation, recognition and retrieval can interlock laterally. It also aligns with the mature Bootstrap `md` anchor and common 768-wide tablet portrait viewports, but the editorial capability is the reason to retain it. |
| `900` | provisional adjustment only | Retain only for a specific content/hierarchy capability that cannot be expressed fluidly inside `768–1399`; otherwise delete/collapse it. |
| `1400` | justified design boundary | Medium field gives way to the wide lateral composition and deliberately uses horizontal space to reduce vertical depth. |
| `1600` | provisional adjustment with one plausible reason | The current implementation reveals the additional Index/Patch return traversal figures here. Retain only if live review confirms that reveal is a meaningful narrative expansion at a useful scale; otherwise delete/collapse it. |
| `1920` | justified design boundary | The page enters the explicit one-screen wide cadence and the complete chapter must fit within 1080 CSS px. |

Do not invent a new threshold during implementation without adding the same kind of
justification to this record (or updating the plan/spec if the change is material).

Current-source evidence gives the two provisional thresholds different starting
weights. `1600` already has a plausible semantic reason: `IndexDeskDocument` reveals
the additional `index-return` and `patch-return` traversal figures only at
`indexQueries.expanded`, so the threshold can earn its place as a deliberate
wide-field narrative expansion if those figures improve the read. By contrast,
current `900` usages are predominantly sizing/placement adjustments in the chapter,
blue carrier, observation and outgoing closing-composition styles. No independent
story beat is presently known to begin at 900. The executor should therefore begin
with a presumption that `900` collapses into fluid `768–1399` geometry unless live
wireframe evidence produces a stronger reason.

### Screen-aware validation without device-authored breakpoints

Responsive-design research supports the same split between editorial authorship and
screen awareness. web.dev recommends choosing major breakpoints from the content,
not device classes. Bootstrap's current mobile-first defaults place `md` at 768px and
`xxl` at 1400px; those are useful, mature anchors but remain subordinate to the
chapter's authored needs.

For this page:

- `768px` is retained because Index gains enough horizontal field for a real
  two-dimensional evidence composition; the fact that it is also a canonical tablet
  / Bootstrap boundary makes it an especially useful real-screen validation anchor;
- `1400px` is retained because the chapter intentionally becomes a wider, shallower
  editorial spread there; its Bootstrap `xxl` familiarity and proximity to common
  1440/1536 desktop widths make it a practical anchor without making Bootstrap the
  author of the page;
- `1920px` is both an editorial transition and a materially real Full HD screen width,
  which is why the one-screen `<=1080px` chapter-height contract starts there; and
- physical display pixels are not breakpoint inputs. HiDPI/DPR and OS/browser scaling
  mean a hardware panel's advertised pixel count is not necessarily the CSS container
  width seen by the page. The live CSS container width is authoritative.

Use real-screen anchors to sample likely viewing conditions, and breakpoint probes to
prove authored transitions. Do not create a breakpoint merely because a screen width
exists.
