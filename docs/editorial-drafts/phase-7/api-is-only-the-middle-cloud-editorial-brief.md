## Start with the correction

The planned article was once called **The API is only the middle**. Harley corrected that framing before this room opened: the API was only an overly narrow example. The governing territory is broader:

> The product is only the middle of engineering.

Writing code and building the product remain skilled, consequential engineering work. Harley's point is that he once mistook that visible centre for the whole job. Good engineering also happens before implementation, and it remains accountable after the first version works.

Do not assume the public title will remain either version of the phrase. Harley decides after discovery.

## Tone and governing-argument posture

This article should feel **warm, pastoral and encouraging**: an experienced engineer talking to somebody earlier in the profession about a view that broadened gradually. It is not a hot take, a fight-me essay, an SDLC explainer or a seniority lecture.

Avoid the smug reading that younger engineers only care about code. Harley did. The code was where he could first see and practise engineering. The eventual point is expansion of responsibility, not a graduation away from implementation or towards management.

## Authority

Harley is the authority on experience, chronology, intended meaning, confidentiality and voice. Repository evidence can confirm public implementation facts; it cannot tell you what Harley learned or what a professional event meant. Ask. Do not fill factual gaps with plausible prose.

You own conversational discovery and manuscript craft under Harley's direction. Keep necessary qualifications. Treat fatigue patterns as editorial evidence, never as automatic rewrite rules.
